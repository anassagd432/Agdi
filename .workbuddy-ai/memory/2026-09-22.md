## Phase 1 TypeScript repair — 45 errors to 0 (direct tsc exits 0)

Finished the TypeScript repair inherited from the prior checkpoint. `tsc --noEmit`
now exits 0, and the public `typecheck` script was changed from
`tsc --noEmit || true` to `tsc --noEmit` and passes. Details in
`docs/audits/phase1-typescript-triage.md`.

Root causes fixed (49 errors total: 45 observed + 4 latent):

- **Cancel/unique-symbol leaks (13).** `@clack/prompts`' `isCancel` narrows to
  `typeof CANCEL_SYMBOL` (a *unique* symbol). Guards written as `(value: T | symbol): T`
  defeat narrowing, because the unique symbol is assignable to the broad `symbol`, so
  inference absorbs the sentinel into `T` and callers see
  `string | typeof CANCEL_SYMBOL`. Correct idiom: declare the parameter as
  `value: T | typeof CANCEL_SYMBOL` (import `{ type CANCEL_SYMBOL }`). Narrowing then
  yields `T` with no cast. This is the reusable lesson for any clack prompt wrapper.
- **`SecretInput` misuse (4).** `FeishuConfig.appSecret` / `MSTeamsConfig.appPassword`
  are `SecretInput` (string *or* secret-ref object), so `.trim()` and passing raw config
  where resolved credentials are required are both wrong. Resolve first
  (`resolveFeishuCredentials`), or reuse the existing
  `hasConfiguredMSTeamsCredentials`. Note `resolveMSTeamsCredentials` also reads
  `process.env`, so it must NOT be used for config-only detection.
- **Missing gateway context member (4).** `jarvisHandlers` calls `context.getJarvis?.()`
  but `GatewayRequestContext` never declared it. Added a structural `JarvisService` type
  plus the optional accessor. There is still no Jarvis implementation in the repo.
- **Dependency version skew, Telegram (1).** The extension resolves `grammy@1.46.0`
  (bundling `@grammyjs/types@5.0.0`) while `@grammyjs/runner@2.0.3` resolves `grammy/types`
  through root `grammy@1.40.0` (`@grammyjs/types@3.28.0`). grammy 1.46 names update types
  the runner's `Update` does not model. Derive the accepted type from the runner's public
  API: `NonNullable<FetchOptions["allowed_updates"]>[number]`.
- **Stale test fakes (8 + 16).** `voice-call/src/manager.test.ts` had a duplicate
  `FakeProvider` missing `getCallStatus`; `manager.test-harness.ts` has the canonical one.
  Channel test nullability: narrow discriminated unions with `if (!result.ok) throw
  result.error` (matches the whatsapp sibling test), hoist guarded consts instead of `!`
  assertions, and use `as WizardPrompter["select"]` for generic prompt mocks (repo idiom).
- **Latent declaration-emit errors (4).** `TS2527` fires under `declaration: true` for
  exported wrappers whose *inferred* type mentions a unique symbol. **TypeScript
  suppresses declaration diagnostics entirely while the program still has semantic
  errors**, so these were invisible at 45 errors and only appeared once everything else
  was fixed. Annotate the return as `ReturnType<typeof clackText>` — type-only, no
  emitted-JS change.

### Second silent false-green found (not fixed — outside file boundaries)

`scripts/generate-base-config-schema.ts` guards its CLI block with
`import.meta.url === new URL(process.argv[1] ?? "", "file://").href`, which can
**never** match: a relative `argv[1]` resolves to `file:///scripts/...` while
`import.meta.url` is `file:///<repo>/scripts/...`, and a Windows absolute path
is parsed as a URL *scheme* (`c:/...`). So `pnpm check:base-config-schema` and
`config:schema:check` are silent no-ops that always exit 0, on every platform.
Proved by calling `writeBaseConfigSchemaModule({check:true})` directly: it
returns `changed: true`. **Correct idiom: `pathToFileURL(process.argv[1]).href`.**
Do not reuse the `new URL(..., "file://")` form anywhere.

## ROOT CAUSE FOUND: per-file-create penalty outside Temp (AGDI)

Supersedes the "fixed 131s overhead" note above (the *number* was right, the
attribution was not).

### npm --timing localises it

`npm install --timing --loglevel=silly` on the slack manifest inside the repo,
total 143.2s:

- npm:load 46ms
- idealTree 20.4s (idealTree:buildDeps 20.4s)
- reify:loadTrees 20.4s
- **reify:unpack 112.8s  <- 79% of the run, the file-writing phase**
- reify:trash 9.2s
- reify total 142.6s

So it is filesystem-bound, not npm resolution logic. (npm's `_timings.json` was
not written anywhere findable; the `timing ... Completed in Nms` lines in the
silly log are the usable data.)

### Filesystem benchmark is decisive

300 files x 2KiB, same script, same drive:

| Operation                        | repo root    | OS temp  |
| -------------------------------- | ------------ | -------- |
| distinct files (create + write)  | 29.71ms/file | 0.38ms/file |
| same file overwritten            | **0.92ms/file** | 0.37ms/file |
| empty files (create only)        | **29.37ms/file** | 0.25ms/file |

**The cost is entirely in file CREATION.** Overwrite is ~1ms; create is ~29ms.
Arithmetic closes: ~4000 unpacked files x 29ms ~= 116s vs reify:unpack 112.8s.

Control at `C:/Users/anass/zzz-fsbench300` (outside the repo, same drive) was
ALSO 29.42ms/file. So it is NOT repo- or `dist/`-specific: everything under the
user profile except Temp pays it. Likely a per-create filesystem filter (the
agent-host sandbox and/or an AV or backup driver); OS queries that would confirm
which are blocked in this sandbox, so the mechanism is inferred from timings
rather than identified.

### Consequences

- `stage-bundled-plugin-runtime-deps.mjs` is NOT at fault and needs no change.
- On a normal dev machine or CI runner (no per-create hook) staging should take
  seconds. The 131s and the ~9min staging estimate are artifacts of THIS host.
- WITHDRAWN: the earlier "npm scans the root 55,737-file node_modules"
  hypothesis. Cost is create-bound and present outside the repo.
- The 33m22s hang remains separate and unexplained (did not reproduce in
  isolation).

### Benchmark method worth reusing

To separate create cost from write cost, run three loops in one script: (A) N
distinct files with payload, (B) N writes to the SAME path, (C) N empty creates
via `fs.openSync(path,"w")`. If A and C are slow while B is fast, it is a
per-create hook. Use Windows-style paths for node arguments.

### Reusable technique: proving a deployed static site == a given commit

1. Fetch production HTML and note the hashed asset filenames.
2. `npm install && npx vite build` locally.
3. Compare emitted asset hashes to the production filenames. Identical ⇒ same build, so
   local `dist/` is a faithful model of production and can be inspected directly.
4. Inspect `dist/` rather than the source: Vite rewrites asset URLs (inlining small files
   as data URIs, hashing large ones). **Do not test source paths like
   `/assets/logos/foo.svg` against production** — I did this first and got 23 false
   "broken image" 404s. The real markup is data URIs. Always re-check findings against
   the built output.

   status code (and for Discord invites, the Discord API rather than the `discord.gg`

### Reusable technique: verify a CODEOWNERS file against the filesystem

    npm run test:package:install-smoke -> All 8 checks passed, exit 0
