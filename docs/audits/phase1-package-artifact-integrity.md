# Phase 1 package artifact integrity

This note covers the package-artifact integrity and runtime-staging workstream:
the host-package rename leak in bundled plugin staging, the declaration artifacts
behind every `types` condition, and the package smoke gate's rule set.

Everything below was measured 2026-09-22 on Windows with Node `v22.22.2`, npm
`10.9.7`, and pnpm `10.32.1` (the pinned `packageManager`). The working tree is
shared with other workstreams, so each result is only valid for the tree state
at the time it was measured.

## 1. What was broken

### 1.1 The host-package rename left `workspace:` in every staged plugin manifest

The root host package is now `agdi`. Bundled plugins declare the host in two
places that are correct inside the monorepo:

- `devDependencies: { "agdi": "workspace:*" }` so plugin sources type-check
  against the local host.
- `peerDependencies: { "agdi": ">=<version>" }` plus
  `peerDependenciesMeta.agdi.optional = true`.

Neither resolves once the manifest is copied into `dist/extensions/<id>/`.
`scripts/stage-bundled-plugin-runtime-deps.mjs` stripped a hard-coded
`openclaw` name only, so the rename left `agdi: workspace:*` behind.

Scope, measured across `extensions/*/package.json`:

| Fact                                                        | Count |
| ----------------------------------------------------------- | ----- |
| Bundled plugins declaring `"agdi": "workspace:*"`           | 84    |
| Bundled plugins declaring `"agdi"` in `peerDependencies`    | 84    |
| Bundled plugins declaring a dependency key named `openclaw` | **0** |

Because no manifest declares the legacy name any more, the hard-coded `openclaw`
branch was dead code, not compatibility.

Reproduction, in an isolated copy outside the checkout, before the fix:

```
npm install --omit=dev --ignore-scripts --legacy-peer-deps --package-lock=false --dry-run
```

Exit 1:

```
npm error code EUNSUPPORTEDPROTOCOL
npm error Unsupported URL Type "workspace:": workspace:*
```

`--omit=dev` does not save this: npm still parses the manifest, so a
`workspace:` spec in `devDependencies` is fatal.

`pnpm build` reached `scripts/runtime-postbuild.mjs`, which calls
`stageBundledPluginRuntimeDeps`, and failed there. Four plugins actually stage
runtime deps — `discord`, `feishu`, `slack`, `telegram` (the ones with
`openclaw.bundle.stageRuntimeDependencies: true`). The other 80 were sanitized
but never installed.

### 1.2 The declaration artifacts were missing, not broken

`scripts/check-package-artifact-smoke.mjs` reported 134 of 274 declared
entrypoints unresolved, all `types` conditions, with zero `.d.ts` files under
`dist/`.

Root cause, traced from source to packaging:

1. `tsconfig.plugin-sdk.dts.json` sets `rootDir: "."` and
   `outDir: "dist/plugin-sdk"` with `include: ["src/plugin-sdk/**/*.ts", ...]`.
   Because `rootDir` is the repo root, `tsc` emits to
   `dist/plugin-sdk/src/plugin-sdk/<entry>.d.ts`, not to
   `dist/plugin-sdk/<entry>.d.ts`.
2. `package.json#exports` points every subpath `types` condition at
   `dist/plugin-sdk/<entry>.d.ts`.
3. The flat entry shims that satisfy those paths are generated by a separate
   build step, `scripts/write-plugin-sdk-entry-dts.ts`, which runs _after_
   `build:plugin-sdk:dts` in `pnpm build`. Its own header comment documents the
   `rootDir` mismatch.

So the declaration pipeline is intact; the step that produces the declared paths
had simply never run, because `pnpm build` was already failing at runtime
staging.

`tsc -p tsconfig.plugin-sdk.dts.json` itself exits 0 with zero diagnostics, both
incrementally and with a forced clean build-info path. The `|| true` that used
to follow it was masking nothing. That suppression has since been removed by
another workstream; this pass provides the independent evidence that the
underlying command passes.

### 1.3 The smoke gate's rules contradicted the repository's own packaging policy

`scripts/release-check.ts` deliberately allows bundled plugin runtime
dependencies in the pack:

```ts
const isAllowedBundledPluginNodeModulesPath = (path: string) =>
  /^dist\/extensions\/[^/]+\/node_modules\//.test(path);
```

`scripts/check-package-artifact-smoke.mjs` forbade _every_ `node_modules/` path.
Once staging worked and runtime deps landed in `dist/extensions/*/node_modules`,
the gate reported 13213 violations, all of them intentional build output. A gate
that flags the intended artifact is not a gate.

A related fact worth recording: `.npmignore` contains `**/node_modules/`, but it
cannot enforce this. `package.json#files` lists `dist/`, and npm does not let
`.npmignore` exclude paths that `files` already included.

### 3.4 Root cause: this host charges ~29ms for every new file outside Temp

`installPluginRuntimeDeps` removes `dist/extensions/<id>/node_modules` and then
runs a blocking `npm install --omit=dev` per plugin, with no output.

**Two controlled A/B pairs, same manifest and same flags within each pair**
(`--omit=dev --ignore-scripts --legacy-peer-deps --package-lock=false`):

| Manifest         | Location                        | Exit | Duration | Packages added | Top-level entries |
| ---------------- | ------------------------------- | ---- | -------- | -------------- | ----------------- |
| discord (8 deps) | inside repo, `dist/extensions/` | 0    | **131s** | —              | 31                |
| discord (8 deps) | outside repo                    | 0    | **15s**  | —              | 31                |
| slack (3 deps)   | inside repo, `dist/extensions/` | 0    | **131s** | 119            | 114               |
| slack (3 deps)   | outside repo                    | 0    | **20s**  | 119            | 114               |

Both inside-repo runs took _exactly_ 131s despite one tree declaring 8
dependencies and the other 3, and producing 31 against 114 top-level entries. So
the cost is a fixed overhead, not per-package work, and the HTTP logs rule out
network: the inside-repo slack run emitted 337 `npm http cache ... (cache hit)`
lines and still reported `added 119 packages in 2m`, while the outside run
emitted the same 337 lines and reported `added 119 packages in 17s`.

`npm install --timing` localises it. Of a 143.2s total:

| Phase              | Duration   |
| ------------------ | ---------- |
| `npm:load`         | 46ms       |
| `idealTree`        | 20.4s      |
| `reify:loadTrees`  | 20.4s      |
| **`reify:unpack`** | **112.8s** |
| `reify:trash`      | 9.2s       |
| `reify` (total)    | 142.6s     |

`reify:unpack` is the phase that writes package files to disk, and it is 79% of
the run. That points at the filesystem, not at npm's resolution logic.

**A filesystem benchmark confirms it.** 300 files of 2 KiB each, same script,
same drive:

| Operation                       | Inside the repo  | OS temp     |
| ------------------------------- | ---------------- | ----------- |
| Distinct files (create + write) | 29.71ms/file     | 0.38ms/file |
| Same file overwritten           | **0.92ms/file**  | 0.37ms/file |
| Empty files (create only)       | **29.37ms/file** | 0.25ms/file |

The cost is entirely in **file creation**. Overwriting an existing file is
0.92ms, creating a new one is 29.37ms, and the same creation in the OS temp
directory is 0.25ms — a **~78x penalty on creating a file outside Temp**. The
arithmetic closes: ~4,000 unpacked files × 29ms ≈ 116s, against `reify:unpack`'s
measured 112.8s.

A control at `C:/Users/anass/zzz-fsbench300`, outside the repository but on the
same drive, was also 29.42ms/file. So this is **not specific to the repository or
to `dist/`** — it applies to new files anywhere under the user profile except
Temp. The likely mechanism is a per-create filesystem filter (the agent host's
sandbox and/or a backup or AV driver); PowerShell/WMI queries that would confirm
which are blocked in this environment, so the mechanism is inferred from the
timings rather than identified.

**What this means.** The staging script is not at fault, and no `npm` or
repository configuration is involved. On a host without this per-create penalty,
such as a normal development machine or a CI runner, staging should cost seconds
rather than minutes. This supersedes an earlier hypothesis in this document that npm was
scanning the repository root's 55,737-file `node_modules`; that hypothesis is
withdrawn, since the cost is create-bound and present outside the repo too.

The candidates tested and eliminated along the way:

| Candidate                                          | Verdict                                                                                                |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Repository `.npmrc` inherited by the child install | Eliminated. It contains only `node-linker=hoisted`, a pnpm setting that npm ignores.                   |
| Root manifest declaring npm `workspaces`           | Eliminated. `package.json` has no `workspaces` field; pnpm uses `pnpm-workspace.yaml`.                 |
| Host bulk-delete guard                             | Eliminated. `fs.rmSync` on a synthetic 80-file directory succeeds inside the repo and under `/tmp`.    |
| Stale npm cache locks                              | Eliminated. Four orphaned `_cacache/tmp` entries, no active lock, no `*.lock` under `dist/extensions`. |
| npm scanning the root `node_modules`               | **Withdrawn.** Superseded by the create-bound measurement above, which also holds outside the repo.    |

## 5. Remaining blockers

### Must be resolved before submission

1. **`bottleneck/.env` ships in the artifact.** The gate is correct to flag it.
   Resolving it is a policy decision, not a code fix, and this workstream did
   not weaken the rule to turn the gate green. Two options:
   - Treat vendored third-party dotenv files as out of scope and scope the
     `dotenv file` rule to first-party paths, matching the hygiene rules. This
     loses the ability to catch a real `.env` that a vendored package ships.
   - Add an explicit, commented exclusion for this path in the packaging policy,
     so the exception is visible and reviewed rather than implied.
     Owner: unset.
2. **`release:check` cannot complete in this checkout.** The gate is a
   `&&`-chain of seven steps, and four of them fail, so it stops long before
   `release-check.ts`. Each step was measured individually:

   | Step                                | Exit | First actionable failure                                                          |
   | ----------------------------------- | ---- | --------------------------------------------------------------------------------- |
   | `check:public-branding`             | 1    | `README.md:1 -> OpenClaw string literal` — a regex false positive, see below      |
   | `config:docs:check`                 | 1    | config baseline drift: `docs/.generated/config-baseline.json{,l}`                 |
   | `plugin-sdk:check-exports`          | 0    | passes                                                                            |
   | `plugin-sdk:api:check`              | 1    | Plugin SDK API baseline drift: `docs/.generated/plugin-sdk-api-baseline.json{,l}` |
   | `stage:bundled-plugin-runtime-deps` | n/a  | not measured standalone, see note                                                 |
   | `ui:build`                          | 0    | writes `dist/control-ui/index.html`, 2.64s                                        |
   | `release-check.ts`                  | 1    | `ENOENT ... open 'appcast.xml'` at `scripts/release-check.ts:212`                 |

   `release-check.ts` aborts inside `checkAppcastSparkleVersions` before any pack
   validation runs. `appcast.xml` is untracked, unignored, and has no git
   history; it is a macOS release artifact produced by `scripts/make_appcast.sh`.
   **Consequence for this workstream:** the shared pack-path policy added to
   `release-check.ts` is covered by its 15 unit tests, not by an end-to-end
   `release:check` run, because that run never reaches pack validation.

   **The `check:public-branding` failure is a false positive, not a real leak.**
   Its `OpenClaw string literal` rule (`scripts/check-public-branding.mjs:70`)
   matches any quoted span containing the bare word `OpenClaw`. In `README.md`
   the match starts at index 18 — the closing quote of `align="center"` on line 1
   — and runs to the next `"` in the file, swallowing the derivation attribution
   on line 25 (`[OpenClaw](https://github.com/openclaw/openclaw)`). The check
   therefore reports `README.md:1`, which is not where the word appears. The
   matched content is an attribution notice, not a product-name string literal.
   Fixing it means tightening the rule or its `targets` list, and `README.md` is
   outside this workstream's file boundary, so it is reported rather than
   changed.

   **Note on the two baseline-drift steps:** `docs/.generated/` holds
   `config-baseline.json`, `config-baseline.jsonl`,
   `plugin-sdk-api-baseline.json`, and `plugin-sdk-api-baseline.jsonl`, all dated
   2026-09-20. They are **not** gitignored (`git check-ignore` returns nothing),
   so a stale baseline is committed state, not a local artifact. Regenerating
   them is `pnpm config:docs:gen` / `pnpm plugin-sdk:api:gen`, which belongs to
   the config-surface and Plugin SDK workstreams. Owner for all four: unset.

3. **`dist/control-ui/index.html` is not produced outside `release:check`.**
   `release-check.ts` requires it. It is generated by `ui/vite.config.ts`
   (`outDir: ../dist/control-ui`) via `pnpm ui:build`, which `release:check`
   runs before `release-check.ts`. A pack taken without `ui:build` will fail
   that path group. Not a defect, but it means the artifact smoke gate is only
   meaningful after a `release:check`-shaped build. Verified: `pnpm ui:build`
   exits 0 in 2.64s and writes `dist/control-ui/index.html`, so this step is not
   itself a blocker — it is only unreached because four earlier steps fail.
4. **The smoke gate is not wired into anything.** No npm script or CI workflow
   invokes `scripts/check-package-artifact-smoke.mjs`; it was run by hand. Its
   self-test is in the same position: `vitest.config.ts` does not include
   `scripts/**/*.test.mjs` and no workflow invokes `node --test`, which the
   CI-integrity workstream independently recorded in
   [Phase 1 CI integrity](/audits/phase1-ci-integrity) — alongside the same
   14-test pass result for this suite.
   It is deliberately not added to `package.json` in this pass, because it
   currently exits 1 on blocker 1 and a script that is known-red should not be
   presented as a gate. Once blocker 1 is resolved, the one-line addition is
   `"check:package-artifact-smoke": "node scripts/check-package-artifact-smoke.mjs"`
   plus an invocation from `release:check`. Owner: unset.
5. **`pnpm build` has never completed on a re-run, and the staging step is slow
   for environmental reasons.** Two separate problems, only one of which is about
   this repository:
   - **Slow, and not ours to fix.** §3.4 identifies the cause: this host charges
     ~29ms to _create_ any file outside Temp, against 0.9ms to overwrite one and
     0.25ms to create one in Temp. That is a ~78x penalty, it holds outside the
     repository as well, and it accounts for `reify:unpack`'s 112.8s. The staging
     script needs no change; on a normal dev machine or CI runner this step
     should take seconds. Four plugins declare runtime deps, so on this host
     staging alone plausibly needs ~9 minutes.
   - **The hang is unresolved.** Four attempts to run the staging path did not
     complete; the last ran 33m22s and was idle for over 30 minutes while
     staging slack (§3.5). **It did not reproduce in isolation** — slack's
     install completed normally in 131s on its own — so the cause is
     unidentified. Contention with stale processes from earlier killed runs is a
     plausible but unevidenced contributor.

   **This is the highest-priority blocker for this workstream**, because until
